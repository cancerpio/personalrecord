# 受眾檢查

在動工前，替 personalrecord 的每個需求多問五題，並**把答案記錄下來**。

## 為什麼需要這個

本專案的最大優勢是作者同時是使用者、領域專家與開發者，需求傳遞零損耗。
同一件事也是最大的盲點：**n = 1**。作者無法從自己身上得知某個需求對別人是否成立。

這個 skill 不是要修正那個盲點——那需要真實使用者。它只做一件事：
**在當下把「這是誰的問題」記下來**，因為這個資訊事後重建不出來。

## 最重要的一條：描述，不是評分

**「只有我會遇到」是完全正常、而且預期中最常見的答案。它不擋任何事。**

這五題 SHALL NOT 被用來決定要不要做、SHALL NOT 影響優先順序、
SHALL NOT 作為說服自己或作者的理由。它們只產生一筆紀錄。

**絕對不要**因為想讓答案「看起來更通用」而修改需求。
**絕對不要**為不存在的使用者設計功能。

理由：本專案之所以持續產出正確的東西，正是因為需求全部來自作者實際使用時撞到的摩擦。
一旦開始替假想使用者做決定，那個迴路就斷了，而迴路斷掉的損失遠大於任何通用性的收穫。

## 五個問題

依序問，答案可以很短。作者答「不知道」也是有效答案，照實記。

1. **這個需求是我用出來的，還是想出來的？**
   來源比受眾更能預測一個功能是不是真的。照實回答即可，「想出來的」不代表不該做。

2. **這是否只解決我個人的問題？**
   描述性問題。答「是」很正常。

3. **進階訓練者是否普遍會遇到？**
   這題作者答得出來——有肌力與體能背景、有訓練同伴、知道別人怎麼排課表。
   這是本專案唯一一題有真實領域知識支撐的受眾問題，值得認真回答。

4. **一般使用者是否也會遇到？**
   作者不是一般使用者，也還沒有一般使用者，所以**任何答案都是推測**。
   因此這題要拆成兩欄回答：
   - **推測**：明確標示為推測，不要寫成事實。
   - **最便宜的驗證方式**：這一欄才是重點。多數時候答案會是
     「給兩三個訓練同伴用一週看他們還會不會用」之類成本接近零的做法。
     沒有便宜的驗證方式時，就寫「目前無法便宜驗證」，不要編一個。

5. **這個功能會不會讓 app 對「我」變差？**
   前四題單向地把思考推往「更通用」，這題是配重。
   為更廣受眾加的東西經常讓唯一的真實使用者體驗變糟——多一個設定、
   多一層選單、多一個要填的欄位。有疑慮就寫下來。

## 答案記在哪裡

記錄是這個 skill 的產出，光問完就散掉等於沒做。依改動規模對應：

| 改動類型 | 記錄位置 |
|---|---|
| architectural（有 design doc） | `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 開頭，獨立一節「受眾檢查」 |
| bounded（無 design doc） | `todo_feature_202608.md` 對應項目底下加一行 `**受眾**：…` |
| 沒有對應 todo 項目的小改動 | commit message 或 PR 描述中一行帶過 |
| spike | 不記錄——spike 的產出是答案，不是功能 |

在 `todo_feature_202608.md` 的項目中，用一行精簡格式即可：

```
**受眾**：用出來的｜僅我｜進階者：是｜一般：推測會（驗證：給訓練同伴用一週）｜對我變差：否
```

## 為什麼要累積

單筆紀錄價值不大，累積二十筆之後會形成一份**自己 app 的通用性地圖**：
哪些部分是純個人的、哪些是進階訓練者共通的、哪些從頭到尾只是推測。

這份地圖有兩個用途：判斷哪些功能值得拿去給別人試用；以及若哪天真的考慮商業化，
它是手上唯一基於長期紀錄而非事後回憶的證據。

## 反面模式

| 想法 | 現實 |
|---|---|
| 「答『只有我』看起來不太好，改一下需求讓它更通用」 | 這正是這個 skill 要防止的事。照實答。 |
| 「一般使用者應該會需要 X，順便加進去」 | 為不存在的使用者設計。不要做。 |
| 「這題我答不出來，跳過」 | 寫「不知道」就是有效答案。跳過會讓紀錄失去意義。 |
| 「Q4 我覺得一般人也會遇到」 | 那是推測，必須標示為推測，並附上驗證方式。 |
| 「這次很小，不用記」 | bounded 的一行標籤成本是十秒。累積價值來自密度，不是單筆。 |
| 「受眾比較廣，所以優先做」 | 這五題不影響優先順序。優先順序由別的因素決定。 |
