# 設計：折線圖從「RM 紀錄」改為「次數趨勢」

日期：2026-09-08

動作詳細面板的折線圖改動。起點是使用者的一句觀察：

> 最近 12 週動作總覽點開來的那個 1/3/5RM 重量折線圖，其實應該是 1 Rep, 3 Rep,
> 5 Rep 的重量趨勢才對，這樣的話就比較合理，也比較有追蹤最近的重量變化的趨勢的功能。
> 因為 1RM / 3RM / 5RM 是紀錄，而不是趨勢，基本上不會往下。

## 受眾檢查

**來源**：用出來的。#26 面板上線後看圖時發現「這條線看起來不像趨勢」。

- **只解決我個人的問題**：是，基本上只有我。
- **進階訓練者是否普遍會遇到**：**部分會**（我提的，使用者未表態）。「紀錄」與
  「趨勢」的混淆是命名問題，任何有輔項訓練（8 下）的人都會撞到「主項有圖、輔項沒圖」。
  但只有自己排課表、且課表包含多種次數方案的人才會在意。
- **一般使用者**：**推測不會**（推測）。**最便宜的驗證方式：目前無法便宜驗證**，
  理由同 #26。
- **對我變差**：否。圖上多了原本看不到的輔項曲線，說明文字只在真的有東西被篩掉時
  才出現，版面不增加固定成本。

## 1. 診斷：資料是對的，名字是錯的

使用者的直覺對，但推論的前提不成立。查 `getChartSeriesForExercise` 的實作：
**篩出 `reps` 嚴格等於 N 的組 → 每個訓練日取當日最大重量 → 連線**。

也就是說那條線從一開始就是「每次做 N 下時做了多重」的趨勢，**練輕的那天就會往下**，
從來不是紀錄線。

錯的是圖例上的 `1RM / 3RM / 5RM`。那三個字的意思是紀錄，於是整張圖被讀成
「紀錄的歷史」，而紀錄不會往下，所以看起來沒有趨勢價值。**這是一次純粹的命名誤導，
資料層不需要動。**

記錄這件事的原因：如果只照字面把需求做成「改成 1 Rep / 3 Rep / 5 Rep」，
會得到一個「改完好像什麼都沒變」的結果，而真正的病因不會留下紀錄。

## 2. 但改名救不了更大的問題

查證（2026-09-08，Firestore `training_sessions` 全庫 529 組）：

| reps | 組數 | 佔比 |
|---|---|---|
| 5 | 190 | 36% |
| **8** | **132** | **25%** |
| 3 | 77 | 15% |
| 1 | 52 | 10% |
| 2 | 28 | 5% |
| 6 | 15 | 3% |
| 其他 | 35 | 7% |

**寫死的 1/3/5 只涵蓋 60% 的訓練。** 最大的缺口是 8 下的輔項。

具體案例——剛結束的分腿蹲週期，Split Squat 全部 20 組清一色 8 下：

```
08-15  40×8 ×4
08-21  45×8 ×5
08-25  45×8 ×5
08-27  45×8 ×4
09-03  45×8 ×4
```

40 kg → 45 kg 的進步曲線，而舊版的 Split Squat 面板**連圖都沒有**
（三個 RM 皆無資料 → 整張圖不顯示）。剛練完一個週期、最想看趨勢的那個動作是空的。

## 3. 決策：線由「該動作實際做過的次數」決定

不寫死次數，改為取該動作出現過的次數方案。使用者核准原話：
「動態 rep 數我覺得 ok」。

**選取**：依**訓練日數**（不是組數）由多到少取前 3 種。用訓練日數而非組數，
是因為一天做 5 組不代表這個次數方案更常用；「幾天做過」才是。

**同數時取次數較少者。** 次數低的是主項，資訊量較高；更重要的是排序必須有一個
確定的規則，否則會隨來源資料順序漂移。

**顯示順序固定由少到多**（1 下 → 3 下 → 5 下），與紀錄排方向一致。
選取用頻率、顯示用次數大小，兩者刻意分開：頻率決定「畫誰」，次數大小決定「怎麼排」。

**上限 3 條。** 沿用舊版的線數，避免圖例爆掉。

**顏色依顯示順序取（綠／藍／紫）**，不綁定次數值。做 1/3/5 的動作因此維持原本配色。
綁定次數值需要為任意 N 準備色票並處理碰撞，複雜度換不到對應價值。

### 說明文字

使用者要求：「請你在圖表的下方或適合的地方簡短的提示這件事，記得簡短扼要，
我不希望版面太雜亂」。

只在**確實有次數被篩掉**時才描述選取規則：

| 情況 | 文字 |
|---|---|
| 有次數未畫出 | `只顯示最常練的 3 種次數 · 每點為當日最大重量` |
| 全部畫出 | `每點為當日最大重量` |

沒篩掉任何東西卻描述一條篩選規則，只是佔版面——這正是他要避免的雜亂。
「每點為當日最大重量」則一律保留，因為那是讀懂這張圖的必要前提
（同一天多組時圖上只有一個點）。

## 4. 順帶修掉的重複計算

新的 `getExerciseRepTrends` 與既有的 `getChartSeriesForExercise`（達成史用）
都需要「每個訓練日、該次數的最大重量」。若各自實作，就會違反 spec 已經寫明的
「達成史與折線圖 SHALL 使用同一份資料，SHALL NOT 各自計算」。

抽出 module 層的 `dailyMaxByReps(sessions, exerciseName)` 供兩者共用，
`getChartSeriesForExercise` 改為呼叫它。連帶效果：

- 舊版以 `record.weight > currentMax`（`currentMax` 預設 0）隱式排除無效重量，
  新版顯式檢查，行為一致但意圖明確。
- 舊版 `s.reps === targetReps` 為嚴格相等，字串型別的 `reps` 會被漏掉；
  新版以 `Number()` 轉換後比對。這只會多納入紀錄，不會少。
- 年月篩選補上 `s.date &&` 保護。

**不移除** `getChartSeriesForExercise`：達成史仍需要「指定 1/3/5」的能力，
而趨勢圖取的是「最常練的次數」，兩者取的次數不同，只是底層計算相同。

## 5. 紀錄排維持原樣

使用者原話：「這個東西目前有記錄日期的方式已經很好了」。1RM / 3RM / 5RM
加首次達成日期不動。紀錄與趨勢分成兩層，正是這次改動確立的框架，
已寫進 openspec 的 Purpose。

## 測試

Store 層新增 10 個測試（`sessionStore.test.js`）：純 8 下的動作有序列、
當日最大重量、由舊到新排序、前 3 種的選取、同數時取次數較少者、
無效 weight/reps 略過、不混入其他動作、空資料回傳空清單，
以及兩個回歸測試鎖住 `getChartSeriesForExercise` 重構後的行為
（嚴格 reps 比對；與 `getExerciseRepTrends` 對同一次數產生**相同序列**）。

元件層無自動化測試（#10 未建立），圖例文字、配色與說明文字以 build + 實機檢視為準。

## 規格同步

`openspec/specs/exercise-detail-panel/spec.md`：
`RM Trend Chart` → `Rep Scheme Trend Chart`（選取規則、顯示順序、圖例命名、
說明文字條件、證據），Purpose 補上「紀錄與趨勢是兩件事」，
達成史那條改為共用「計算」而非共用「資料」。
