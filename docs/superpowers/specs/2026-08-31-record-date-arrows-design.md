# 設計：Record 頁日期左右箭頭（±1 天）

日期：2026-08-31

## 目標

在 Record 頁的日期列加上左右箭頭，一個 tap 切換前後一天。

## 受眾檢查

- **來源**：使用時撞到的。原始訴求是「切換日期還要點開（原生選擇器）超不方便」。
- **只解決我個人的問題**：否——想快速翻看過去某一天是通用需求。
- **對我變差**：否。不增加任何垂直高度，原有的原生選擇器保留。

## 資料佐證

比對 484 筆紀錄的 `date` 與 `createdAt` 的本地日期：

| | 筆數 | 佔比 |
|---|---|---|
| 當天記錄 | 465 | 96.1% |
| 補記過去 | 19 | 3.9%（**全部都是前一天，無一超過 1 天**） |
| 記到未來 | 0 | 0% |

因此「回到昨天」是唯一實際發生過的日期操作，值得一個 tap 就到。

**但這組數字只涵蓋寫入行為，看不到瀏覽行為**——使用者切到過去某天只看不改時不留痕跡。
曾據此得出「不需要月曆」的錯誤結論，詳見 todo #20。本項的箭頭同時服務兩種行為，
不受該限制影響。

## 決策

### 1. 箭頭放在既有日期列內，不增加高度

`‹ 2026-08-31 ›`，左右各一個 32px 觸控目標，中間仍是原本的 `input[type=date]`。
點日期本身照舊開啟原生選擇器，供跨度較大的跳轉使用——箭頭是捷徑，不是取代。

### 2. 不允許往未來走

`canGoNextDay` 在 `selectedDate >= 今天` 時停用「下一天」，且 `stepDay` 內再擋一次
（按鈕停用只擋滑鼠，程式或鍵盤觸發仍需防線）。

**理由**：本 app 是紀錄工具而非計畫工具；資料中未來日期為 0 筆；不擋的話連點兩下
就會靜默記到明天，而錯誤日期的紀錄事後很難發現。

**解除此限制的條件**：使用者指出另一款 app `Mohup` 並不擋未來日期，因其定位偏向
**預先安排課表**。若本專案日後往「先排課表、再對照執行」的方向走（與 todo #14、#2 相關），
屆時要處理的是**在資料模型上區分「計畫」與「已執行」**，而不是單純放行未來日期。

### 3. 停用時降透明度而非隱藏

隱藏會讓按鈕消失、日期左右跳動。固定位置比省下 32px 重要。

### 4. `shiftDays` 從 store 搬到 `src/utils/date.js`

原本是 `sessionStore.js` 的私有函式，RecordView 取用不到。**與其複製一份，不如搬家**——
`utils/date.js` 本來就是放純日期運算的地方，搬過去後 sessionStore 改為 import，
兩處共用同一份實作，並獲得單元測試覆蓋。

搬移時保留註解說明它與 `todayLocalISO` 的分工：後者從「當下時間」取日期、會受時區影響；
`shiftDays` 的輸入已是日期字串，做的是純日曆運算，因此 `Date.UTC` 才是正確寫法。

## 明確不做

- **鍵盤導覽**：按鈕為原生 `<button>`，本身可 focus 與觸發，但未額外處理焦點管理。
- **長按連續切換**：實測補記從未超過 1 天，沒有需求。
- **顯示星期幾**：與本項無關，未納入。

## 測試

- **`shiftDays` 完整 TDD**：先 RED（6 個測試失敗）後 GREEN。涵蓋前後平移、跨月、跨年、
  閏年（2028-02-29 與 2026 非閏年）、補零、以及「純日曆運算不受時區影響」。
- **按鈕接線無自動化測試**：Vue 元件互動測不了（todo #10）。
  人工驗證：點 `‹` 回到昨天、連點回到更早、在今天時 `›` 呈停用、點日期仍可開原生選擇器。
