# 設計：體組成收斂到 Dashboard

日期：2026-09-06

#26 動作詳細面板上線後的第二批調整（第一批見
`2026-09-06-easy-max-and-overview-wording-design.md`）。三個改動共用同一條原則：
**體組成只有一個地方看，動作面板只回答訓練表現。**

不改資料模型，不新增任何寫入路徑。

## 受眾檢查

**來源**：用出來的。#26 上線後實際看 Dashboard 撞到的摩擦——面板裡的體重與頂部
12 週圖講同一件事、footer 那句話太囉嗦、想在同一處看體脂。

- **只解決我個人的問題**：是，基本上只有我。
- **進階訓練者是否普遍會遇到**：**不知道**（使用者原話）。這是五題中唯一有領域知識
  可支撐的一題，而他選擇不猜——照實記，不補一個聽起來合理的答案。
- **一般使用者**：**推測不會**（標示為推測，我提的）。「資訊該擺哪一層」是使用超過
  一個週期後才會浮現的問題，一般使用者多半還沒累積到會在意的量。
  **最便宜的驗證方式：目前無法便宜驗證。** 與 #26 同因——身邊可接觸的訓練同伴
  都屬進階者，不構成一般使用者樣本。
- **對我變差**：**待驗證，做出來才知道**（使用者原話）。已知的風險是 footer 多了
  一行字，而 Dashboard 過長本來就是他的長期抱怨。

## 1. 動作詳細面板：移除體重與體脂率

使用者原話：「移除體重，只顯示重量，以後這邊只會有訓練表現，體重／體脂率在
Performance Overview 上面的 Dashboard 顯示」。

### 決策

**兩條序列都移除，不只體重。** 需求只點名體重，但「以後這邊只會有訓練表現」
把體脂也劃了出去。折線圖回到單軸（右軸原本只為體脂率而存在）。

這推翻了 #26 當時寫進 spec 的理由——當時主張「面板的每日體重對照該動作當天的
重量」與「頂部的每週平均體重」是兩件不同的資訊。該理由本身沒有錯，但被
「體組成只有一個地方」這條更強的原則取代：分散在兩處的代價（每次要問「我剛剛
看的是哪一張圖的體重」）大於每日對照的邊際價值。**此處記錄的是取代，不是修正。**

**圖下的說明文字一併刪除。** 那句話（`chartDesc`）的職責是描述疊圖由哪幾條線
組成；疊圖沒了之後它只剩「左軸為訓練重量 (kg)」，而圖例已經說明每條線是什麼。
此項為我提議、使用者核准（原話：「我覺得你說的都 ok, 都做吧」）。

### 明確不做

**不刪 store 的 `getChartSeriesForBodyWeight` / `getChartSeriesForBodyFat`。**
兩者在移除疊圖後已無呼叫端（`App.vue.bak` 不算）。留著的理由：它們是目前唯一
會產生「每日體組成序列」的程式碼，而這次的改動方向正是把體組成集中到 Dashboard——
日後若要在 Dashboard 做每日尺度的體組成視圖，需要的就是它們。使用者未要求刪除，
不順手擴大範圍。

## 2. Dashboard footer：兩行 12 週基準

### 文案

| | 原本 | 改為 |
|---|---|---|
| 容積 | 過去 12 個完整週平均：5,901 kg／週（不含本週） | 過去 12 週平均容積：5,901 kg（不含本週） |
| 體組成 | （無） | 過去 12 週平均體重／體脂率：81.0 kg／—（不含本週） |

刪掉的兩處都是重複：「完整週」的資訊已由「不含本週」表達，「kg／週」的「／週」
已由「平均」表達。

### 數字來源：不另算一份

`weeklyTrainingVolumeInfo` 內部本來就在算 12 週基準體重（給標頭 chip 當比較對象），
只是沒回傳。這次把它 `return` 出來成為 `baselineBodyWeight`，並以同一條規則
（`baselineOf`）加上 `baselineBodyFat`。footer 顯示的體重因此**永遠等於** chip 的
比較基準——不是兩個湊巧相同的數字。

原本的 `getWeeklyBodyWeightAverages` 一併改寫為 `getWeeklyMetricAverages(metrics, field)`，
體重與體脂共用同一份週分組邏輯。**兩者各自判定缺值**：量了體重不代表當天也量了體脂。

### 連帶的行為變更：基準先四捨五入

差值改為「當週平均 − **四捨五入後的**基準」。原本用未四捨五入的基準，兩者最多差
0.05 kg。之所以要改：基準值自此會直接顯示在畫面上，若 chip 仍用未四捨五入的值，
會出現「底下寫 80.0、上面寫當週 80.5、chip 卻標 +0.6」這種自相矛盾。
這是既有「先四捨五入再判定」原則（2026-08-23）的延伸，不是新規則。

### 空狀態：保留欄位，顯示破折號

使用者選擇。查證（2026-09-06，Firestore `body_metrics` 全庫）：**沒有任何一筆
`fatPercentage`**——這一格在他開始量體脂之前會一直是「—」。

這與 Easy Max「沒有 1RM 就不顯示佔位符」的決定相反，理由不同：Easy Max 缺席是
因為那個動作**沒有 1RM 這回事**，補一個破折號等於假裝它存在；體脂缺席只是
**還沒量**，欄位在才看得出這格量了就會有數字。

（此處也是 2026-09-06 記取的教訓的直接應用：查到資料是空的不是移除功能的理由。
使用者原話：「別移除, 這個我猜還是需要, 只是我不會那麼頻繁的量體脂」。）

## 3. 12 週圖加入體脂率折線

使用者原話：「同以前選 1RM / 3RM / 5RM 圖表的呈現方式一樣，用虛線（或者你覺得
更好的顯示）折線圖顯示週平均的體脂率」。

### 第三個 Y 軸

使用者的疑問：「26% 會跟 y 軸共用單位嗎，他的位置就會是 26kg 嗎？」

不會。體脂用**獨立的第三軸**，自己的 min/max（例如 14–22%），只是與容積、體重
共用同一塊繪圖區。26% 會被畫在「26 在該範圍內的相對位置」，與 kg 無關。
代價是紫線與橘線可能視覺交叉，而那個交叉點沒有任何意義。

### 體脂軸不畫刻度

右側已有一排體重刻度，LIFF 手機寬度再擠一排會蓋住圖面。這條線負責形狀，
數值走 tooltip。**取捨已明確告知使用者**：紫線的高低不能直接讀出數字。
他選擇先看實際畫面再決定要不要補刻度。

### 樣式

| | 顏色 | 線型 | 標記 |
|---|---|---|---|
| 週容積 | 藍（accent） | 長條 | — |
| 週平均體重 | 橘 `#D97706` / `#FF9F0A` | 實線 | 圓點 |
| 週平均體脂率 | 紫 `#AF52DE` / `#BF5AF2` | `ShortDash` | 菱形 |

不用同橘系的第二個色階：兩條同色系的細線在手機寬度下分不出來。虛線與色相兩層區隔。

**標記保留（不同於動作面板舊版的體脂線）。** `connectNulls` 為 `false` 時，
被 null 包夾的孤立一週若沒有標記會**完全畫不出來**。以他目前的量測頻率，
「只有一週有體脂」正是最可能的情況。

### 軸範圍

沿用體重軸的夾制策略，量級換成百分點：最小跨度 4、最大 20（體重是 8 kg / 50 kg）。
最小跨度防止 0.2% 的波動被放大成懸崖，最大跨度防止離群值把線壓平。

### 全無資料時完全不留痕跡

12 週內沒有任何體脂紀錄時，序列不加入圖表、圖例不出現該項、tooltip 也不顯示體脂列。
一行永遠寫著「體脂率：無紀錄」的 tooltip 只是噪音。**這是他現在會看到的狀態。**

## 測試

Store 層（`sessionStore.test.js`，9 個新測試）：基準跳過空白週、不含本週、
視窗外不計入、四捨五入到小數一位、無資料為 `null`、空字串與非數字不影響結果、
每週體脂缺值為 `null`、同週多筆取平均、體重與體脂各自缺值。

元件層無自動化測試（#10 未建立），文案、圖表配色與軸行為以 build + 實機檢視為準。
**體脂折線本身在正式資料下畫不出來**（無資料），要等實際量測後才驗得到。
