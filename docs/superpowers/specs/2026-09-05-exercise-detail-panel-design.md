# 設計：動作詳細面板（紀錄、達成史、近 14 天明細）

日期：2026-09-05

## 目標

在「最近動作總覽」的任一列點開一個手風琴面板，同時回答排課表時要問的兩件事：
**這個動作我的紀錄是多少**（1RM / 3RM / 5RM）、**最近兩週我實際做了什麼**
（哪幾天、幾組、幾下、多重）。

## 受眾檢查

**來源**：用出來的。原話：「經過一個週期後，我在回顧並思考下一個週期應該怎麼安排訓練時想到」。

- **只解決我個人的問題**：是，基本上只有我。
- **進階訓練者是否普遍會遇到**：**部分會，看訓練型態**——自己排課表的人需要回頭分析，
  跑固定課表或跟教練的人不需要。這是五題中唯一有領域知識支撐的答案。
- **一般使用者**：**推測不會**（標示為推測）。
  **最便宜的驗證方式：目前無法便宜驗證。** 身邊可接觸的訓練同伴都屬進階者，
  不構成一般使用者樣本。不編造一個。
- **對我變差**：**待驗證，做出來才知道**。與 #22 相同——手風琴預設全收合會讓
  Dashboard 變短，但多了一層點開收合的操作，實際好壞要用過才知道。

## 起因

上個週期（分腿蹲 + 輕舉重，約 2.5 週）結束，下週回高背槓深蹲。排課表時需要
最大重量與訓練容積兩個指標，但**不同動作看的重點不同**：深蹲／硬舉／臥推兩者都要看，
分腿蹲／划船或增肌週期只需要容積。原始訴求是「避免資訊過於雜亂」，
因此走「總覽表 + 點開詳細」而非把所有東西攤在 Dashboard 上。

## 查證：三輪推翻了三次設計

本次設計有三個版本被實際資料推翻。過程記錄如下，因為推翻的理由本身就是規格的一部分。

### 第一輪：「1RM/3RM/5RM 三條線直接畫上去」——嚴格 reps 讓一半動作無圖

原始想法是不給使用者選 RM 類型、三條直接畫。查 2026-08-12～09-03（上個週期，
155 筆）每個動作的 reps 分佈：

| 動作 | 組數 | reps 分佈 | 嚴格 1/3/5RM 可用組數 |
|---|---|---|---|
| Hang Snatch | 28 | 3×15, 5×13 | 28 |
| Bench Press | 27 | 1,2,3,4,5,6,7,8 皆有 | 12 |
| **Barbell Row** | 23 | **全部 8 下** | **0** |
| **Split Squat** | 20 | **全部 8 下** | **0** |
| Hang Clean | 19 | 3×4, 5×15 | 19 |
| Deadlift | 16 | 1×10, 2, 3, 5 | 14 |
| **Barbell Overhead Press** | 11 | 4,5,7,8 | **1** |
| High Bar Squat | 7 | 1×3, 3×1, 5×3 | 7 |
| **RDL** | 4 | **全部 8 下** | **0** |

`getChartSeriesForExercise` 用的是**嚴格 reps 相等**（`s.reps === targetReps`），
不是「至少 N 下」。因此划船、分腿蹲、RDL 三個動作（47 組、佔 30%）圖表全空，
肩推只有一個孤點。

**這剛好是使用者點名「只需要看訓練容積」的那幾個動作**，所以語意上通，
但意味著近半數動作的強度圖不存在。

順帶查到一個支持「兩個指標不可互相取代」的事實：臥推 08-30 是**最重的一天**
（75×1×4 組），卻是**容積最低的一天**（620，其他天 1500～2100）。

### 第二輪：「每日最重一組」——技術上最好，但不是使用者要的東西

為解決涵蓋率，改為「每個訓練日取最重的那一組、不限 reps、標註 reps」。
資料上它確實是唯一會動的線：

```
Bench Press    05-12 72×5 → 05-18 75×4 → 06-01 起 60×8 平原（七週）→ 08-30 75×1 → 09-02 62×7
Barbell Row    05-10 65×5 → 07-31 45×8 → 08-15 40×8 → 08-27 47×8 → 09-02 47×8
High Bar Squat 05-10 125×1 → 06-04 70×5 → 07-01 100×5 → 08-12 110×1 → 08-16 50×5
```

**被使用者否決**，原話：

> 最大重量我通常只需要看到歷史以來最大的，當天的最大重量我通常不是自己記得
> 就是沒什麼機會想去看這個，除非我很懷疑 PR 記錯了才會一個一個點開來看。

這句話是本次設計的轉折點——它指出兩個**不同頻率**的需求：
平常看歷史紀錄，懷疑時才查證。後者才是「每次訓練的重量」的真正用途。

### 第三輪：「累積最佳（running max）折線」——幾乎是水平線

改為只升不降、不斷線的累積最佳。算出每條線實際「動」了幾次：

| 動作 | 1RM | 3RM | 5RM |
|---|---|---|---|
| Deadlift | 05-14→140，之後完全水平 | 05-14→120，水平 | 05-14→100，水平 |
| High Bar Squat | 05-10→125，之後完全水平 | 05-10→100, 05-18→107 | 05-10→105, 05-18→107 |
| Bench Press | 05-12→72, 08-30→75 | 05-12→72, 05-18→75 | 05-12→72，水平 |
| Barbell Row | 線不存在 | 線不存在 | 05-10→65，水平 |
| RDL | 線不存在 | 線不存在 | 05-27→80，水平 |
| Split Squat | 線不存在 | 線不存在 | 線不存在（整張圖空） |

**10 個動作、30 條可能的線裡，只有 3 條變動超過一次，最多的一條只有 2 階。**
這張圖承載的資訊 = 三個數字 + 三個日期，卻佔約 200px。因此累積最佳改為**靜態文字**。

## 決策

### 1. 面板結構：三塊，由上而下

```
▼ Deadlift ────────────────────────────────
   1RM  140  (05/14)                  ▸
   3RM  120  (05/14)                  ▸
   5RM  100  (05/14)                  ▸
   ─────────────────────────────────────
   〔1RM / 3RM / 5RM 折線圖 + 體重／體脂疊圖〕
   ─────────────────────────────────────
   近 14 天
   08-30    6組 · 容積 1,390
            100×5  120×3  130×1×3  140×1
   08-23    5組 · 容積 920
            100×3  120×1  120×2  130×1×2
```

點紀錄列的 `▸` 展開該 RM 的完整達成史（使用者原話的「一個一個點開來看」）：

```
   1RM 歷史（reps = 1）
   08-30  140      06-06  140
   08-23  130      05-24  140
   08-16  130      05-17  140
   07-05  130      05-14  140
```

**達成史與折線圖是同一份資料的兩種呈現**——都是「該 reps 每日最重」，
即現成的 `getChartSeriesForExercise(ex, rmType, 'all', 'all')`。
因此展開達成史不需要新的資料來源，`HistoryChart.vue` 也得以保留重用。

### 2. 折線圖與靜態紀錄排並存

三輪查證後，使用者選擇兩者都要。理由是它們回答不同問題：
靜態排回答「我的紀錄是多少、多久沒破」，折線圖回答「這個 rep 區間的表現怎麼變化」。

**已知代價**：划船、分腿蹲、RDL 的折線圖是空的或只有一條。
三個 RM 序列皆無資料時整張圖 SHALL 不顯示（不是顯示空圖）。

### 3. 手風琴，而非捲動到常駐區塊

#22 當時的機制是「點列 → 捲到頁面下方常駐的 Performance Overview 區塊」，
且該區塊在載入時會自動選第一個動作。詳細內容從一張圖變成三塊之後，
那個常駐區塊在使用者還沒點任何東西前，就佔著一大塊版面顯示一個**任意挑到的動作**——
這正是當初移除 Sparkline 的理由之一（`uniqueExercises.value.slice(0, 3)` 的任意性）。

**改為手風琴，預設全部收合，同時只展開一列。** 單開而非多開的理由：
Dashboard 過長是使用者的長期抱怨（見 2026-08-29 設計文件的受眾檢查第三題），
多開會讓 12 列的表變成無限捲軸。

### 4. 容積視窗固定 14 天，沿用總覽表

評估過四個選項。查每個動作在各視窗內的訓練日數（基準日 2026-09-05，
2026-05-10 起 378 筆）：

| 動作 | 近14天 | 近28天 | 「最近 6 次」需回推 |
|---|---|---|---|
| **High Bar Squat** | **0** | 2 | 62 天 |
| **RDL** | **0** | 1 | 不足 6 次 |
| Deadlift | 2 | 3 | 92 天 |
| Hang Clean | 2 | 4 | 67 天 |
| Bench Press | 3 | 6 | 22 天 |
| Barbell Row | 3 | 6 | 22 天 |
| Split Squat | 3 | 5 | 不足 6 次 |
| Hang Snatch | 6 | 9 | 12 天 |

固定 14 天的已知缺點是**使用者最在乎的主項目恰好頻率最低、因此最看不到**——
高背槓深蹲 0 天、硬舉 2 天。設計討論時推薦的是「最近 N 次有練到的日子」
（每個動作永遠有內容、視窗長度自動適應頻率），**但使用者選擇固定 14 天**，
理由是與上方總覽表語意一致。此決定記錄在案，若日後覺得主項目看不到，
這裡就是要改的地方。

### 5. 空視窗顯示「上次」的內容

14 天內無紀錄時 SHALL 顯示「近 14 天未練 · 上次 MM-DD」加上那次的完整內容。
理由是成本幾乎為零（資料本來就要掃），而回高背槓深蹲時需要的正是這一行。

**已知限制（重要）**：「上次」不保證有代表性。高背槓深蹲最後一次是 2026-08-16 的
`50×5 ×2 組`（分腿蹲週期裡的維持性輕組），對排下個週期的參考價值有限。
這是資料的實情，不是設計缺陷，但不應假裝這一行永遠有用。

### 6. 保留體重／體脂疊圖，隨圖表一起搬進面板

底部 Performance Overview 的橘色虛線讀 `fatPercentage`。查全庫 `body_metrics`
（查詢日 2026-09-06）：**整個集合只有一筆有 `fatPercentage`（2026-03-29、25.6），
且屬於已不再使用的 userId `Ubbd3d4b2fe12d1739beee79da781e06b`；
目前帳號 `U55e58505…` 從 2026-04-08 至今一筆都沒有。**

**但這不構成移除的理由。** 使用者說明體脂是「不會那麼頻繁地量」，不是不要——
輸入路徑存在（`RecordView.vue` 有欄位）、getter 正常運作，缺的只是量測頻率。
因此疊圖保留，隨 `HistoryChart.vue` 一起搬進詳細面板。

體重折線同樣保留。它與頂部 12 週容積圖的體重**不是同一個量**：
頂部是每週平均，疊圖是每日值對照該動作當天的重量（既有的交叉判讀）。

**原始問題另解**：舊區塊的說明文字寫著「右側虛線代表體脂率 (%)」，
描述的是一條當時畫不出來的線。做法沿用 RM 空序列的既有慣例——
序列無資料時不加入圖表，圖例便不會出現該項，說明文字也不再承諾不存在的東西。

**代價**：面板內的圖最多五條序列（3 RM + 體重 + 體脂），比原本的三條密。
三個 RM 皆無資料時整張圖仍不顯示，不會只為了體重／體脂而畫一張與該動作無關的圖。

| 項目 | 處置 | 查證依據 |

| `FilterControls.vue` | 刪除 | rmType（三條全畫）／exercise（點列取代）／year・month（單一動作最多 15 個訓練日，篩選無意義）四個控制項全部失去對象 |

刪除死碼的理由是死碼比沒有程式碼更糟。代價是**年月篩選能力消失**——
目前資料量下（每個動作最多 15 個訓練日）不成問題，但若某個動作累積到數年、
上百個訓練日，折線圖會過密。這是刻意接受的取捨。

## 資料層

兩個新 getter，職責分開：

```js
getExerciseRecords(exerciseName)
  → { 1: {weight, firstDate} | null,
      3: {...} | null,
      5: {...} | null }

getExerciseRecentDetail(exerciseName)
  → { days: [{date, sets, volume, groups: [{weight, reps, count}]}],   // 新到舊
      lastBefore: {date, sets, volume, groups} | null }                // days 為空時才有值
```

### 邊界決定（沿用既有慣例，不另創規則）

- 紀錄日期取**首次達成日**，不是最近一次——它回答「這個紀錄多久以前立的」。
- `weight` 缺失、空字串或非數字的紀錄在紀錄計算中**略過**（同 `exerciseOverview` 的 `maxWeight`）。
- 容積用 `(reps || 0) * (weight || 0)`（同 `weeklyTrainingVolumeInfo`）。
- 同一天相同 `weight` + `reps` 的多筆紀錄合併為 `count`（顯示為 `45×8 ×4`）。
- 同一天內的組合依重量由小到大（同重量再比 `reps`）。來源順序不保證穩定，
  顯示順序必須確定；由小到大也對應暖身到主組的實際進行順序。
- 三個 RM 皆無資料時整排不顯示，分隔線也不顯示。
- `lastBefore` 只在 `days` 為空時才有值。
- **不做動作名稱別名合併**——`Overhead Press` 與 `Barbell Overhead Press` 仍是兩個動作
  （沿用 2026-08-29 的決定，讓 #12 的問題保持可見）。
- 未來日期的紀錄會落進 14 天視窗，與 store 其他部分一致（屬 #25 的範圍，不在此處解決）。

### 一致性

總覽表「最重」欄取不限 reps 的最大重量，與詳細面板的 RM 紀錄**是不同的量**，
可能不相等（例：分腿蹲最重 45，但三個 RM 皆為 null）。這是刻意的，
沿用 `exercise-streak-overview` spec 已明文規定的「最大重量 ≠ PR」。

## 明確不做

- **e1RM（估算 1RM）**。評估過，能讓不同 rep 區間可比（臥推 e1RM 在六月起的
  60×8 平原期穩定在 76，而「當日最重」看起來是從 75 掉到 60）。但 todo #21 已記錄
  兩點：舉重動作（Hang Clean / Snatch）受技術與速度限制，e1RM 會產生看似精確
  但無意義的數字；且 #21 已將 e1RM 列為延後。導入需分動作處理，範圍大於本次需求。
- **每日最重一組的折線**。使用者明確否決，見〈第二輪〉。
- **當日容積長條圖**。與折線圖組成雙軸圖曾是候選，未採用。
- **紀錄的達成次數（幾天／幾次）**。查證時發現這個訊號成本近零且能讓孤例自行浮現
  （深蹲 1RM 125 與 #21 那筆錯誤的臥推 100×3 形態相同），但**使用者未提出此需求**，
  本次不做。#21 整項（含存檔當下的即時 PR 通知）維持在本次範圍外。
- **鍵盤操作**。可點擊的列為 `div` + `@click`，與專案既有做法一致。
- **Dashboard 區塊開關**（#23）。仍等本次改動的實際使用回饋。

## 測試

兩個新 getter 全部 TDD，先 RED 後 GREEN。至少涵蓋：

- `getExerciseRecords`：三個 RM 皆有資料／部分為 null／全為 null；
  首次達成日而非最近達成日；無效 `weight` 略過。
- `getExerciseRecentDetail`：視窗邊界（第 14 天算、第 15 天不算）；
  同 `weight`+`reps` 合併為 `count`；容積計算；`reps` 缺失不成 `NaN`；
  `days` 為空時回 `lastBefore`；完全無紀錄時 `days` 為空且 `lastBefore` 為 `null`。

**元件層無自動化測試**——前端元件測試基礎設施尚未建立（todo #10），
與 #22 相同。手風琴展開／收合、單開行為、達成史展開皆以人工驗證。
這是本次改動最大的弱點，如實記錄。

## 已知風險

**Highcharts 在收合的容器內初始化會量到寬度 0**，展開時需要觸發 reflow。
`DashboardView.vue` 已有既有處理（`nextTick` 後 `dispatchEvent(new Event('resize'))`），
同樣手法可用，但這是本次唯一的實作風險點。
