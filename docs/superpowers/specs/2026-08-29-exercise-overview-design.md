# 設計：最近動作總覽（訓練量與最大重量）

日期：2026-08-29

> 本文為事後補寫。原本判定為 bounded 而未產出設計文件，實作過程中範圍長大（見文末
> 〈分類的檢討〉）。文中記錄的替代方案都是當時真的權衡過的，不是追認。

## 目標

在一個地方一目瞭然看到：最近兩週練了哪些動作、各做了多少組與次數，
以及該動作歷來最重多少。

## 需求來源與受眾檢查

**來源**：使用時撞到的。

**受眾**：僅我／進階訓練者／一般使用者三題，作者的回答皆為**「不知道」**——如實記錄。
這一項目前沒有任何受眾證據，若日後要判斷是否值得給別人試用，應從這裡開始補。

**對我變差**：原設計（Dashboard 新增一塊）**會**——作者明確表示 Dashboard 已經太長。
這個回答直接推翻了原本的版面決定，見〈決策 2〉。

## 探索發現：「PR」這個詞已經被佔用

需求原文說的是 PR，本意是 1RM，但作者指出「有些動作根本不會去做 1RM」，
因此改為取最大重量。

讀 code 時發現 `getChartSeriesForExercise` 的 `calculationType = 'PR'` 已經是
**嚴格 1RM**（`reps === 1` 的最大重量），且註解寫明是刻意的：
「Users want strict classification, not at least X reps」。

若新功能也叫 PR，同一個詞在兩處會有不同意義。這是本專案已經吃過虧的問題類型
（連續週數的錨點語意、動作名稱分岔）。

## 決策

### 1. 「最近兩週」＝滾動 14 天，不沿用週界

**選項**：滾動 14 天 vs 本週＋上週（週一起算，沿用 12 週容積與連續週數的週界）。

**選擇滾動 14 天。** 理由是它任何時候看到的都是完整兩週；週界版本在週一早上會退化成
「上週 + 今天」，涵蓋範圍在 8～14 天之間浮動。

**代價**：同一個元件內存在兩套時間範圍。這是刻意的，因為它們回答不同問題——
週界回答「這一週有沒有練到」，滾動 14 天回答「最近兩週累積了多少」。
已寫進 spec 與程式碼註解，避免日後被「統一」掉。

### 2. 合併進既有表格，而非新增區塊

原本已決定「Dashboard 新增一塊」，但受眾檢查第三題（「加進去會不會讓 Dashboard
對你變難用」）的回答是「**會，Dashboard 已經太長了**」，推翻了該決定。

重新檢視後發現：新表與既有的「最近動作連續週數」**本質相同**——都是以動作為列、
都在回答「我最近在練什麼」。分成兩塊才是真正的冗餘。

**評估過三個版面**：

| 方案 | 結果 |
|---|---|
| 合併成一張表（四欄） | **採用**。Dashboard 不變長，資訊密度提高 |
| 合併但每個動作佔兩行 | 否決。資訊全保留，但列高變兩倍、12 筆變 24 行，Dashboard 反而更長 |
| 兩塊分開 | 否決。Dashboard 再長一截，且動作名稱會重複列兩次 |

### 3. 命名為「最大重量」，圖表的 PR 維持 1RM

三個選項：沿用 PR 並改掉圖表定義／沿用 PR 但圖表維持 1RM（同詞兩義）／另取名稱。

**採用「最大重量」，圖表不動。** 兩個概念各自有名字，日後不會混淆，
也不必更動既有圖表行為。已在 spec 中以 SHALL NOT 明文禁止兩者混用名稱。

**已知限制**：純看最大重量會忽略 reps，100kg×1 與 100kg×10 都是 100。
對「這個動作我碰過最重多少」是正確的，但不反映高反覆區間的進步。作者已知並接受。

### 4. `exerciseStreaks` 更名為 `exerciseOverview`

它現在回傳的不只是連續週數，沿用舊名即為語意漂移。元件 `ExerciseStreakList.vue`
一併更名為 `ExerciseOverview.vue`（`git mv` 保留檔案歷史）。

**代價**：改名動到 store、測試、DashboardView、spec 四處，diff 比功能本身大。
此代價向作者揭露過並取得同意。

### 5. 移除「最後練到」欄

四欄（動作／最近14天／最重／連續）是手機版面的上限。`lastDate` **仍然回傳、
仍然用於排序**，只是不顯示——連續週數已隱含近期性。

日後若要加第五欄，必須犧牲現有欄位之一，不能硬塞。

### 6. 視窗內無紀錄顯示破折號，而非「0組·0次」

`0組·0次` 會被讀成「練了但沒記到數字」；破折號才是「這段期間沒碰」。
已寫進 spec，免得日後被當成不一致而「修正」。

## 資料處理的邊界決定

- 一筆紀錄＝一組。`recentSets` 為視窗內筆數。
- `reps` 缺失或非數字時以 **0** 計入該筆，避免總和變成 `NaN` 汙染整欄。
- `weight` 缺失、空字串或非數字的紀錄在計算最大重量時**略過**；
  完全沒有有效重量時回傳 `null`，由畫面顯示破折號而非 0。
- **未來日期的紀錄會落在視窗內**。這與 store 其他部分一致；防止未來日期屬於
  輸入驗證，是另一件事，不在此處解決。

## 明確不做

- **不顯示「這 14 天有沒有破最大重量」。** 有價值，但屬另一項工作。
- 不重新命名 capability 目錄 `exercise-streak-overview`。範圍已擴大，
  但改目錄名會破壞既有參照，代價大於效益；已在 spec 的 Purpose 註明。

## 測試

getter 可完整 TDD，先 RED 後 GREEN。新增 7 個測試：組數與總次數、
視窗邊界（第 14 天算／第 15 天不算）、最大重量不受視窗限制、視窗內未練回 0、
無效 `weight` 略過、完全無有效重量回 `null`、`reps` 缺失不成 `NaN`。
另更新 3 個既有斷言（回傳物件多了三欄）。全套 75 個通過。

元件為純表現層、不含計算，且前端元件測試基礎設施尚未建立（todo #10），故不另寫測試。

## 分類的檢討

**一開始宣告為 bounded，事後看應為 architectural。**

判定 bounded 的理由是「與 `exerciseStreaks` + `ExerciseStreakList` 同一形狀，
有現成流程可抄」。但實際包含了既有 getter 與元件改名、一個 capability 的範圍擴大、
以及既有元件欄位結構的改動——符合 brainstorming skill 對 architectural 的定義
（restructure how components fit together / alter interfaces others depend on）。

更關鍵的是 skill 明訂「hidden complexity discovered mid-task upgrades the path —
stop, say so, and step up」。**範圍在過程中長大，但未停下來重新分類。**

此事直接促成流程調整：自 2026-08-29 起，除非另行指示，**所有需求一律產出 design
doc**，使分類判斷失誤不再造成決策理由遺失。
